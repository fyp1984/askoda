# Askoda

> 数据需求智能分析助手 —— 业务用自然语言提数据需求，系统给出「口径明确、可解释、可审计」的 SQL。

Askoda 面向**高合规行业的数据取数场景**。它的目标不是"把问题翻译成 SQL"这么简单，
而是让每一次取数都留下可追溯的判断链：**这句话是怎么被理解的、用了哪张表、口径从哪里来、
生成前后的每一道门禁拦了什么、谁在什么时候执行过、结果为什么被判定为可交付**。

## 一、核心特性

| 特性 | 说明 |
|---|---|
| **需求受理与结构化** | 一句业务口吻的需求 → 结构化需求（指标 / 维度 / 过滤 / 颗粒度 / 时间窗），带 schema 契约校验 |
| **语义层约束生成** | 不做自由生成，先把候选对象收敛到语义层（MDL）可见范围；未命中即拒绝，不猜 |
| **五层 SQL 门禁** | L1 语法（sqlglot）→ L2 AST 静态规则 → L3 只读门禁 → L4 语义层 dry-plan 校验 → L5 结果断言 |
| **澄清问答闭环** | 口径不明时生成澄清问题、回填答案并留痕，不以默认值静默兜底 |
| **只读执行** | 生成的 SQL 一律经语义层执行，物理层不做写操作 |
| **九字段留痕 + 审计回放** | 每次执行记录需求版本、语义层版本、规则版本、生成 SQL、门禁结论、执行人……可完整回放 |
| **双库可换** | 同一套代码接两套语义层（裸库 A / 已治理库 B），换库零代码改动 |
| **失败回退矩阵** | F1–F5 分类明确失败归属，用于判定"该补元数据、补规则还是补确认" |

## 二、架构

```
业务端（Agent / 客户端）
        │
        ▼
自建统一前端 ──► FastAPI 网关 / BFF ──► MCP 网关（FastMCP 2.x, streamable-http）
                                              │
                        ┌─────────────────────┼─────────────────────┐
                        ▼                     ▼                     ▼
                  Wren 语义层 A         Wren 语义层 B         知识底座 / 元数据库
                  （电商域 裸库）      （零售会员域 已治理）   （RAGFlow 检索 / 附件存储）
```

架构上守三条底线：

- **网关侧不内置 LLM**。语义分析走「证据编排 + 确定性规则」，每条结论带来源与置信度；
  需要自由生成的部分交由客户端 Agent。因此本项目不绑定任何具体模型。
- **不做 fork、不改开源引擎源码**。定制一律走官方扩展点或外挂层。
- **第三方能力收口**。门禁 → `gateway/gates.py`、契约 → `gateway/contracts/`，便于替换与升级。

## 三、目录结构

```
askoda/
├── gateway/          网关服务端（MCP 工具面 41 个）：受理 / 分析 / 生成 / 门禁 / 执行 / 留痕
│   ├── contracts/    对外契约（结构化需求 schema 等）
│   ├── Dockerfile
│   └── requirements.txt
├── tools/            自证与独立复扫脚本（每个里程碑一套，含对抗用例）
├── poc-eval/         POC 评估与端到端演练（题库、回放、演练脚本、机器可读报告）
├── knowledge/        知识底座样例文档（指标口径 / 安全办法 / 表结构 / 受理规程）
├── wren-docker/      模拟库 A 环境（电商域，6 模型 / 29 字段 / 5 关系）
├── wren-docker-b/    模拟库 B 环境（零售会员域，8 模型 / 47 字段 / 10 关系）
├── demo/             演示程序（本地实测服务 + 可交互 Demo 页面 + 品牌资产）
├── docker-compose.yml    一键起停编排（网关 + 双库 + 元数据库 + 附件存储）
└── .env.example      环境变量样例（复制为 .env 使用）
```

> 项目管理类文档（PRD、技术方案、作战计划、验收单、归档）**不在本仓库内**，
> 独立维护在项目文档工作空间中。本仓库只保留工程文件与面向开发者的说明。

## 四、快速上手

前置：Docker（本机为 OrbStack）、Python 3.11+、`docker` 命令可用。

```bash
# 1. 准备环境变量
cp .env.example .env

# 2. 起停全部服务（网关 + 元数据库 + 附件存储 + 双库，共 7 个服务）
docker compose up -d
docker compose ps

# 3. 改了 gateway/ 代码后重新构建
docker compose up -d --build
```

> ⚠️ macOS + OrbStack 下，`compose build` 需要把 buildx 配置目录重定位到仓库内
> （沙箱不允许写 `~/.docker/buildx`）：
> ```bash
> BUILDX_CONFIG="$PWD/.buildx" docker compose build gateway
> ```

### 接入面

| 项 | 地址 | 说明 |
|---|---|---|
| MCP 端点 | `http://127.0.0.1:18080/mcp` | streamable-http，Agent 接这里 |
| 健康检查 | `http://127.0.0.1:18080/healthz` | 各数据集与组件连通性 |
| 模拟库 A | `127.0.0.1:9000`（MCP）/ `15432`（PG） | 电商域，6 模型 |
| 模拟库 B | `127.0.0.1:9002`（MCP）/ `15433`（PG） | 零售会员域，8 模型 |
| 网关元数据库 | `127.0.0.1:15434`（PG） | 需求单 / 事件 / 元数据字典 |
| 附件对象存储 | `127.0.0.1:19000`（S3）/ `19001`（控制台） | MinIO |
| 知识底座 | `http://127.0.0.1:19380/api/v1` | RAGFlow 检索接口（网关只做客户端） |

宿主机网关端口用 `18080` 而非 `8080`：`8080` 留给本地演示服务 `demo/demo-server.py`。

## 五、验证

```bash
# 工具面与 MCP 层验收（41 个工具 + 真实调用比对）
python tools/mcp_acceptance_check.py

# 门禁层自证
python tools/gates_selftest.py

# 端到端演练：主线故事 + POC-1 题库复跑 + POC-3 陷阱用例 + MDL 事实核对
python poc-eval/poc_e2e_gateway.py        # 产出 poc-eval/e2e-gateway-report.json
```

需要容器内跑的脚本（依赖网关内部模块）用法见各脚本头部注释，统一是：

```bash
docker cp tools/<脚本>.py demand-gateway:/app/tools/<脚本>.py
docker exec -e PYTHONPATH=/app demand-gateway python /app/tools/<脚本>.py
```

> 注意：`tools/` 不在镜像构建上下文内，**每次 `docker compose build` 后容器内 `/app/tools/` 会被清空**，
> 需重新 `docker cp`。
