# 本体 / 术语平台选型调研：企业端多语言审批链与版本发布要不要上重型平台

> 状态：调研结论（v1.0，2026-11-01）
> 适用问题：Askoda 将来做「面向企业端交付的多语言审批链 + 版本发布平台」时，是否需要引入
> VocBench / PoolParty / TopBraid EDG / Skosmos 这类本体平台。
> 事实来源：本次检索到的公开资料（见文末）。**版本号与商业条款签约前须复核**——本文的
> 结论不依赖具体版本号，只依赖各产品的能力边界。

## 一、结论先行

**现在不需要引入任何重型本体平台；将来也只会在两类信号出现后才需要，而且很可能仍然不需要
PoolParty / TopBraid 这一类商业套件。**

理由不是"我们自研更强"，而是这三件事被混为一谈了：

| 常被混为一谈的三件事 | 实际是什么 | 现在归谁 |
|---|---|---|
| 术语/口径**定义**（怎么算、叫什么） | 数据 | Askoda：`db/credit/04_metrics.json` → MDL |
| 术语/口径的**治理**（谁改、谁批、发哪版） | 流程 | Askoda 现有：留痕 + 门禁 + 版本号；**缺审批链与发布基线** |
| 术语/口径的**发布**（对外可查、可引用） | 站点 | 现在没有，将来可上 Skosmos 一类只读发布层 |

重型平台卖的是"治理 + 发布"这两层，**而这两层我们目前一条真实需求都还没有**：
现在只有一个域（信贷）、一套口径（10 条）、一个维护人。用 TopBraid EDG 的授权费与建模人力，
去换一套 10 条口径的审批流，是把组织问题当成软件问题买。

## 二、把"企业端交付"拆成可判定的需求

先把模糊的"多语言审批链和版本发布"拆成 8 条可判定需求，再逐条看有没有现成方案。
拆不开就会陷入"平台功能对比"，永远比不完。

| # | 需求 | 判定线 | 现状 |
|---|---|---|---|
| N1 | 一个概念多种语言的标签（中/英，可能日/繁） | 需要 `prefLabel@zh`、`prefLabel@en` 并存 | 无（现在是中文单语） |
| N2 | 同义词/缩写/"业务方言"归到同一概念 | 一个概念可挂多个 altLabel | 部分（`aliases` 已是这个作用） |
| N3 | 编辑 → 校验 → 发布 的角色分离 | 至少 3 种角色：编辑、审核、发布 | 无（一人可改可发） |
| N4 | 变更影响分析（改这条口径会影响哪些需求/SQL） | 能反查引用 | **半有**：`knowledge_citations` + 口径对象留痕可反查 |
| N5 | 版本发布与回滚（口径的 v1.2 可整体回退） | 有版本号 + 可切回 | **半有**：`04_metrics.json` 有 `version`，回退靠 git |
| N6 | 对外可引用（URI 稳定、可解引用） | 概念有稳定标识 | 无 |
| N7 | 自动标引：把文档自动挂到概念上 | 千份级以上文档时必需 | 无，也**暂时不需要**（当前文档量级是几十份） |
| N8 | 权限与审计（谁在何时改了什么） | 可追溯 | **有**：留痕表 + 门禁 |

**关键观察**：真正缺的是 N1（多语言）、N3（角色分离）、N6（对外引用）；
N2/N4/N5/N8 已经有一半以上，N7 是"文档量级问题"，不是"平台问题"。

## 三、四类工具的定位与边界（按能力，不按品牌）

| 工具 | 是什么 | 强在哪 | **做不到什么（决定性的）** |
|---|---|---|---|
| **Skosmos**（芬兰国家图书馆，MIT） | 只读**发布**前端：概念页、层级树、多语言检索、REST/Linked Data | 部署轻（Docker）、URI 可解引用、多语言浏览体验好；FAO AGROVOC、EU、UKDS 都在用 | **没有编辑器**：用户管理、变更管理、质量管控都不提供。欧盟 Joinup 的评估直接写"不适合用户管理/质量管理/变更管理" |
| **VocBench 3**（FAO + 罗马二大，BSD-3） | 协作**编辑**后端：SKOS/SKOS-XL/OWL/OntoLex | 角色细分（编辑/校验/发布）、变更历史、回滚、多语言标签（支持数十种语言）、FAIR 8/8 | **没有**自动标引/文本抽取/推荐；**没有**单语言切换视图；OWL 2 DL 只部分覆盖；自建要 Tomcat + MySQL + 三元组库 |
| **PoolParty**（Semantic Web Company → 现属 Graphwise） | 商业"语义中间件"：词表 + **自动标引** + 语义检索 | 大规模非结构化内容的自动/半自动标引、多语言抽取（含中文）、与 CMS/搜索集成 | 治理深度不如 TopBraid；定位偏内容侧；界面偏工具化、学习曲线高 |
| **TopBraid EDG**（TopQuadrant，商业） | 商业"数据治理套件"：术语表 + 词表 + 本体 + 参考数据 + 血缘 + 策略 | SHACL 强校验、审批流、变更影响、RBAC，与数据目录/血缘一体 | 无公开定价、需销售；上手陡（功能 4.8/5 但易用性 2.3/5、易部署 1.9/5）；对"只治理一套词表"明显过重 |

一个被反复验证的部署形态：**VocBench（编辑）+ Skosmos（发布）+ 三元组库**。
FAO AGROVOC（3.2 万概念、最多 23 种语言）、UKDS 的 HASSET/ELSST（约 3300 概念，2020 年从自研迁到此组合）都是这个组合。
反过来说：**这两个"重型"开源件是可以拼起来用的，而且拼起来的运维成本并不低**（Java + PHP + SPARQL 三套栈）。

另一条更轻的路子（"两个工程师的项目"范式）：**SKOS 存 Git + 三道校验（Skosify 结构、qSKOS 质量、自定义 SHACL 业务规则）+ Skosmos 内网发布**。
零许可成本，代价是协作靠 MR、发布按月。

还有一个容易被忽略的事实：**SKOS 本身是刻意"低语义承诺"的**——它保留 `broader` 这类关系但不强制形式化。
AGROVOC 曾整体转成 OWL 类层级，最后又转回 SKOS。这说明大多数术语/口径场景**不需要推理机**，
需要的是"唯一说法 + 可查 + 可追溯"。

## 四、对照我们的场景：什么时候该上，上哪个

| 触发条件（出现任一条再动手） | 该上什么 | 为什么不是别的 |
|---|---|---|
| 客户要求口径**对外开放引用**（对方系统要拿 URI 取口径说明） | **Skosmos**（只读发布，Docker 一个容器） | VocBench 管编辑不管发布；商业套件为这一件事上不值 |
| 编辑人 ≥3 人 / 跨机构 / 需要"编辑-审核-发布"角色分离（N3） | **VocBench 3**（零许可）或先自研"口径变更单 + 双人复核" | 自研审批流在只有一种变更类型（改口径）时更省；跨机构、要角色矩阵时 VocBench 更划算 |
| 术语要同时服务**多语言交付**且标签量上千（N1） | VocBench 3（多语言标签 + 角色），发布配 Skosmos | Skosmos 能展示多语言但不能编辑 |
| 需要对**上千份文档做自动标引/实体抽取**（N7） | **PoolParty** | VocBench/Skosmos 完全不做抽取；这是 PoolParty 唯一无法替代的能力 |
| 受监管行业要求术语与**数据血缘、策略、审计**联动 | **TopBraid EDG** | 唯一把治理链条打通的产品；代价是预算与专职建模人力 |
| 只是想"让业务方查得到口径、别再发明第四种说法" | **现有 04_metrics.json + 前端展示页**，最多加 Skosmos | 这一类需求根本不需要平台 |

**Askoda 的判断线**：
- 现在（单域、10 条口径、1 个维护人）→ **什么都不上**，把口径注册表打磨好即可；
- 融资/POC 阶段出现的真实诉求是"客户要能查、要能追"，→ **先做前端口径页 + 变更留痕**，不引入新系统；
- 交付形态变成"多客户、多语言、多审核人"时 → **VocBench（编辑）+ Skosmos（发布）**，这两个是开源、可私有化、可离线，符合我们的部署偏好；
- 只有当客户明确提出"文档自动打标"时，才评估 PoolParty（且要重点验中文抽取准确率）；
- TopBraid EDG 只在"金融监管级语义治理"这种项目里作为投标选项出现，不作为平台底座。

## 五、和现有架构怎么接（不要制造第二套真相）

现有链路已经是单向的：**口径（数据）→ 规划器（编译）→ SQL → 门禁 → 留痕**。
将来上任何平台，都必须保持这个方向，**不许反向**（不许让平台去"生成 SQL"，也不许让 SQL 逻辑回流到词表里）：

```
[词表/本体平台]  权威定义（SKOS：prefLabel/altLabel/definition/version）
        ↓ 同步（只读，单向）
[04_metrics.json] 口径注册表：view / expr / dims / time_mode / caveats
        ↓ tools/credit_metrics.py --apply
[MDL]            views（引擎展开）+ x_askoda_metrics（规划器读）
        ↓
[metric_planner] 口径 → SQL（通用编译，新库只登记不改码）
        ↓
[门禁 + 留痕]     闭集/只读/语义/需求覆盖 + 每次引用可回放
```

一旦引入 VocBench/Skosmos，唯一要新增的是"词表 → 口径注册表"的同步适配器（把 SKOS 的
`prefLabel`/`altLabel`/`definition` 映射成 `label`/`aliases`/`definition`），
**口径注册表仍是编译产物，不是第二份定义**。

反过来，如果先自研审批流，也建议把"变更单"做成结构化的（谁、改了哪条口径、影响哪些视图、
谁复核、发哪版），因为这份数据将来能直接喂给 VocBench 的变更历史，不会白做。

## 六、明确不建议（以及原因）

1. **现在给 WeKnora 开图谱抽取**：它做的是"文档 → 实体关系图"，改善召回，不产出"问题 → SQL"；
   上次实测已证明会让入库跑不完、门禁假红。
2. **Neo4j / Memgraph 独立图库**：多一套备份/监控/账号体系，收益要等真有"多跳推理"需求（担保圈、集团口径）才成立。
3. **为 10 条口径上 TopBraid / PoolParty**：能力过剩 10 倍，成本与运维却是实打实的。
4. **先建"完整本体"再谈取数**：本体的价值在"被消费"，没有消费方的本体只会腐化；
   我们的顺序反过来——**先有口径（能被 SQL 消费），再补术语治理**，这也是本项目一路验证有效的顺序。
