## 五、已闭合（本批内完成，列此备查）

### 本批（第三批 · 2026-10-23 晚间：把「能答但答错」逐条杀掉）

> 主线：本题集把 34 题跑到 100% 之后**没有停**——继续拿"更刁的说法"去撞规划器，
> 撞出 8 处「**SQL 能跑、门禁能过、但答的不是人家问的**」。这类缺陷最贵：
> 没有报错、没有红门禁，业务方不看列名就会拿去汇报。逐条修如下。

- **#20 分组内取最大（原题集 B-30）**：「各门店销售额最高的月份」原本退化成
  「按门店排名」——**问哪个月最好，答成哪个店最好**。改为 `ROW_NUMBER() OVER
  (PARTITION BY 门店 ORDER BY 金额 DESC)` 取 `名次=1`。同族把维度换成品类也补上：
  「各门店销售额最高的品类」同样会丢品类列，一起修。
- **#19 跨指标组合（原题集 B-29）**：`各门店会员数和销售额` 只出会员数。
  根因是两个指标来自不同表（`dim_member` / `dwd_order_di`），线性分支结构做不到。
  新增 `_store_metric_combo()`：各指标先按门店各自聚合，再 `LEFT JOIN` 对齐。
  **用 LEFT 不用 INNER**（否则没会员的门店会凭空消失，而那恰是最该看的一行）；
  **缺数留 NULL 不补 0**（NULL＝确实没有，0＝算出来是零，抹平就是把"没有"谎报成"零"）。
- **同比 / 环比（新能力）**：以前整段丢失（返回一张普通月度销售额表）。
  新增 `_yoy_mom()`，口径写死三条：
  ① **按日历自连接**求基期（`月份 - INTERVAL '1 month' / '1 year'`），
     **不用** `LAG(...,1)`。理由：月份连续时两者结果完全一样——如今库正好连续，
     看不出区别；一旦某月缺数，行号窗口会拿两个月前的数当"上月"、13 个月前的当
     "去年同期"，**结果照样出、门禁照样过，只是数字错**。与 REQ-COVERAGE 同一病理。
  ② 基期为 0 用 `NULLIF` 把增长率置 NULL（基数 0 时增长率无定义，报 0% 或无穷大都错）。
  ③ **基期金额列一起输出**（去年同期销售额 / 上月销售额）：基期缺数时增长率整列空，
     不给基期金额，业务方分不清"没有可比数据"还是"系统算错了"。
  实测：环比 8 月 +21.65%、9 月 −2.0%（与手算一致）；同比因库中无 2025 年数据全为
  NULL，`去年同期销售额` 列同步为空 —— 这正是设计意图（说清原因，不编数）。
- **组合分支吃掉排名**：「各门店会员数和销售额排名」得到的是按**门店名**排的表。
  排序是有的，只是排在错的列上——比"没有排序"更难发现（SQL 里有 ORDER BY、
  门禁看不出问题，只有做"前十名"时才发现顺序不对）。补 `ORDER BY 销售额 DESC
  NULLS LAST`（NULL 排最后，不当 0 参与比较）+ 前N名的 `LIMIT`。
- **中位数给成合计**：「各门店销售额中位数」原本返回 `SUM`。中位数的意义正是
  「不被少数大额订单拉高」，换成合计等于把这个问题本身取消了。引擎实测
  `MEDIAN()` ✅ / `PERCENTILE_CONT` ❌，改用前者（不做假设，先测再用）。
- **「每天」丢日粒度**：「各门店每天的销售额」只按门店汇总 ⇒ 趋势、异常日、活动
  效果全没了。补日粒度分支，日期用业务日期 `order_date`（不是装载时间）。
- **「前N名」只排序不限行**：「各门店销售额前三名」返回全榜单。补 `_topn()`，
  中文数字（前三名）与阿拉伯数字（前 3 名 / top5）都认；只排序不限行＝把前三名
  悄悄变成全榜单，业务方贴进汇报就是整张表。
- **L2 `GROUP_BY_INCONSISTENT` 改成逐层判定**：原实现 `find_all(exp.Group)` 会把
  子查询的 GROUP BY 抓上来跟外层投影比 ⇒ 必然误报；上一轮改成"只看根 SELECT"
  虽然不误报了，但**CTE 内部真缺列也一起看不见**（误报换成漏报，更糟）。
  正解：遍历每个 Select，只处理**自带 GROUP BY** 的那些，各按自己的投影判。
  判据成对写：CTE 合法结构「不该报」+ CTE 内部真缺列「仍要报」。
- **L2 `TIME_FIELD_SUSPECT` 别名展开补派生表前缀**：`ORDER BY m.月份` 里 `m` 是
  CTE 名、`月份` 是 `date_trunc(...)` 的别名，却被当成物理列判"非标准时间列"——
  每个月度 SQL 都挨一枪，警告多了就没人看警告。现在：**前缀不属于 MDL 真实表/模型
  ⇒ 认定为派生表，继续展开别名**；`dw_insert_time AS 月份` 照样被抓。
