# 需求受理与口径确认规程

本文件说明数据需求从提交到进入分析要经过哪些环节，以及什么情况下必须回头找业务确认。

## 一、提交时必须提供什么

| 字段 | 必填 | 说明 |
|---|---|---|
| 需求标题 | 是 | 一句话说明要解决的问题 |
| 业务背景 | 是 | 为什么要做、面向谁使用 |
| 需求说明 | 是 | 业务自然语言描述 |
| 输出预期 | 是 | 希望拿到什么结果或表样 |
| 联系人 | 是 | 后续确认的责任人 |
| 时间范围 | 否 | 涉及的业务时间区间 |
| 期望完成时间 | 否 | 便于排期与优先级判断 |
| 附件与表样 | 否 | 表格、截图、文档、示例记录 |

**关于"必填"的口径**：业务背景、需求说明、输出预期这三项**同时不完整**时，
需求不允许提交——缺了这三项，分析人员无法判断要解决什么问题。
其余必填字段（如联系人）缺失时会给出提示，但不阻断提交。

## 二、提交时的四道校验

| 校验 | 触发条件 | 处理方式 |
|---|---|---|
| 核心字段完整性 | 背景、说明、输出预期同时不完整 | **拒绝提交**，要求补齐 |
| 附件可识别性 | 附件格式系统无法自动解析 | 提示在需求说明中补充文字描述 |
| 重复需求检查 | 与历史需求高度相似 | 提示优先复用，并列出相似需求单号 |
| 时间范围自洽性 | 描述含强时间口径但未填时间范围 | 提示补充明确区间 |

"强时间口径"指的是近 30 天、本月、上季度、同比、环比、日均、滚动等表述。
这类表述**必须落到具体日期区间**才能分析——比如"近 30 天"到底以哪一天为基准日，
不同理解会得出不同结果。

## 三、什么情况下必须回头确认

以下情形出现时，必须向业务方确认，不能由分析人员自行拍定：

1. **不同知识来源对同一口径给出冲突解释**。例如两份文件中"复购率"的分母定义不一致。
2. **无法判断一行数据代表什么**。颗粒度不明确，会直接决定结果对不对。
3. **时间口径会直接影响最终结果**。例如"本月新增会员"是指注册口径还是首单口径。
4. **输出字段存在多种业务解释**。例如"销售额"是含退款还是不含退款。
5. **用户补充了新材料**，且新材料足以推翻原有结论。

## 四、向业务问什么、不问什么

**只问会影响结果的问题。** 例如：
- "您说的活跃会员，是当月有下单记录，还是会员状态标记为活跃？"
- "这个销售额要不要含退款单？"
- "统计口径是按订单日期还是按核销日期？"

**不向业务问技术问题。** 例如"这两张表用哪个字段关联""要不要加去重"——
这些是分析人员和技术人员的职责，抛回业务既得不到答案，也增加了业务负担。

## 五、需求状态流转

| 状态 | 含义 |
|---|---|
| 待分析 | 需求已受理，进入分析队列 |
| 分析中 | 分析人员正在拆解 |
| 待业务确认 | 已形成需确认的问题，等待业务答复 |
| 待补充修改 | 业务已答复或补件，等待重新整理 |
| 待审核通过 | 已形成结构化需求，等待审核 |
| 已通过 | 可流转至技术环节 |
| 已退回 | 信息不足或方向错误，需重新提交 |

**确认与答复的历史不可覆盖。** 每一轮的问题、答复、时间与版本都要留痕，
不允许用新答复直接覆盖旧记录——否则后续复盘时无法还原当时为什么这样判断。

## 六、被退回的需求怎么处理

被退回的需求必须明确展示退回原因和需补充项，业务方据此补充后重新提交。
补充说明不等同于推翻原需求，原需求单的编号与历史答复继续保留。
